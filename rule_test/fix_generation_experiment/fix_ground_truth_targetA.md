## Notes

- **A1/A3/A5 and A2/A4/A6 (TomaszRewak_MAGI/ai.py)** are three structurally identical pairs, one per function (`is_yes_or_no_question`, `get_answer`, `classify_answer`). Each function receives its own `key: str` parameter and reassigns `openai.api_key = key` immediately before its own `openai.ChatCompletion.create(...)` call — the key is not constant across the file, so a single module-level client cannot be shared between the three functions. The correct migration constructs a fresh, locally-scoped client per function (`client = openai.OpenAI(api_key=key)`) and calls `client.chat.completions.create(...)` in the same function. I used `openai.OpenAI(...)` (fully qualified through the already-imported `openai` module, since the file only has `import openai`, no `from openai import OpenAI`) so that each fix stays confined to its own line and does not require also editing the import statement. - **A7 (franalgaba .../app.py:41)** is a genuine case where a clean single-line fix requires inlining client construction, because no module-level `openai.api_key = ...` assignment exists anywhere in this file to migrate into a shared client. (The file does load `OPENAI_API_KEY = os.environ["OPENAI_API_KEY"]` at line 21, but that variable is dead — never referenced again in the file — so the v0.x code was relying on the `openai` package's own auto-read of the `OPENAI_API_KEY` env var at import time, which has no v1 equivalent to migrate.) This is functionally correct but re-instantiates a client on every call rather than reusing one — noted here because it is a real, evident semantic wrinkle, not because the *line's own required text* is uncertain.
